# Brandi's Fork — A Sovereign Ecology

## What This Is

This is a personal ecosystem — a system for organizing projects, knowledge, and creative work that grows from your own friction rather than following someone else's categories. It is built on a small set of structural commitments (the kernel) and a set of operational protocols (the trunk) that together provide a substrate for any domain you bring to it.

The kernel was forked from an existing ecology that proved these patterns across multiple unrelated domains. The domain-specific content was stripped. What remains is the structural logic — tested, general, and ready to fill with whatever you bring to it.

Any Claude session opening this project should read this file first, then read the kernel and trunk documents it references before engaging with work.

- **Virtue questions are narrative, not systemic.** When presenting a decision fork, frame it as a situated vignette — the shape of the situation, the tension, the characters (projects, tools, constraints) — not as a multiple-choice list of system options. Brandi grips the narrative; the narrative grips the system decision underneath. The meaning precedes the mechanic.

## The Kernel

The foundational structural commitments live in `kernel/`. They are the minimal set of positions that all projects inherit holographically:

| Document | Position |
|---|---|
| `kernel/node.md` | A node is sovereign. It can be read alone and understood as what it is. |
| `kernel/relation.md` | A relation is intersubjective. Both sides describe it from their own perspective. Neither contains the other. |
| `kernel/provenance.md` | Provenance is deterministic. Who, when, from what. Structural facts, not narrated accounts. |
| `kernel/node_schema.md` | Molecular composition of the three positions. What emerges when they compose: the sovereignty test, the adapter boundary, holographic emanation. |
| `kernel/schema.md` | What the graph has discovered about itself. Emergent node types, edge types, the current topology. |

These positions are abstract — they describe how any node, relation, or provenance chain works, not what specific nodes exist. Your ecology fills them with your own material.

| Protocol | Document | What It Does |

| **Opportunistic Separation** | `trunk/opportunistic_separation.md` | Stand up projects the moment separation of concerns becomes visible. Cost of premature separation ≈ 0. |

## How the Ecology Grows

The ecology starts with this kernel and these protocols. As Brandi works on projects, the ecology grows:

1. **Projects appear** when separation signals crystallize — different toolchain, different lifecycle, different failure modes. Each gets its own directory and governing document.
2. **The schema fills** as the graph encounters new kinds of nodes and relations. `kernel/schema.md` accretes from what actually exists, not from what was planned.
3. **Procedural memory deepens** as real operational friction produces Graveyard and Gold entries.
4. **The omnibus grows** as tags accumulate across projects, revealing dark patterns and strange attractors.
5. **Trunk protocols may evolve** as Brandi's friction reveals improvements or new protocols worth sharing across branches.

Each branch project is a holographic shadowmapping of the kernel — it projects the full structural logic (sovereignty, composition, adapter boundaries, provenance) into its domain at the resolution that domain requires. A creative writing project doesn't need build toolchain knowledge. A coding project doesn't need color theory. But both express separation of concerns, FADE ingestion, procedural memory, and sovereignty at the scale of what they actually are.

## The Hybrid Codex Pattern

Every significant document follows this structure:

**Zone 1 — Routing Header**: What this document is, what scope it governs, where to jump. Traffic control.

**Zone 2 — Human Profile**: Meaning layer. Philosophy, vision, intent, locked decisions and rationale. Natural language. Legible ambiguity.

**Zone 3 — Machine Profile**: Execution layer. Paths, patterns, versions, hard rules, syntax, known working procedures. Dense, compressed, operational.

A single document holds both. No parallel documentation.
